# Rust 与 gpui 宿主的测试稳定性

Lithe 现在只有两个 Rust 测试面。判断一条规则适不适用，先问"这个测试在哪个面"。

## Rust Core（`rust/lithe-core`）

确定性业务逻辑：不碰 UI、不持有长生命周期资源、不起子进程。测试就是普通
`cargo test`，下面大部分风险在这里天然不存在。

- **不要为了"更真实"而在 Core 单测里起真进程**。Core 收到的是命令信封，
  它解析请求、返回结果；需要真实 `git` 或 JDTLS 的行为属于集成验证，
  要显式标注，不能混进单元测试。
- **fixture 用 `shared/fixtures/**` 里的共享样本**，不要在测试里内联一份同样的
  JSON —— 那会让契约漂移无法被发现。
- **顺序与格式必须确定**。Core 的返回值是兼容面：列表要排序、路径用工作区相对
  路径 + `/`、行号从 1 开始、缺失位置用 `null`。

## gpui 宿主（`rust/gpui/crates/*`）

这里是**真正会挂 CI** 的地方。宿主持有窗口、后台线程、channel、文件监听、
终端 PTY 和 JDTLS 子进程。

### 不要在单元测试里启动真实外部资源

| 想验证的东西 | 不要这样 | 应该这样 |
| --- | --- | --- |
| JDTLS 会话 | 真起一个 JDTLS 进程 | 在 `java/src/session.rs` 的 trait 后面注入测试替身；需要真实 JDT 的行为走显式集成验证 |
| 终端 | 真开一个 PTY | 喂一段已录好的 ANSI 字节流，断言解析与渲染 |
| 文件监听 | 真建监听再等事件 | 直接调用事件处理函数，事件是参数不是等待 |
| 工作区快照 | 依赖磁盘上的真实项目 | 用 `shared/fixtures/projects/**` 里的夹具，或在临时目录里搭最小结构 |

### 等待必须有本地截止时间

```rust
// 错：卡住就只能等 CI 超时
let line = reader.next().await;

// 对：任何一条路都必须在 deadline 内收敛
tokio::select! {
    Some(line) = reader.next() => handle(line),
    _ = tokio::time::sleep(DEADLINE) => panic!("no output within {DEADLINE:?}"),
}
```

`select!` 的每个分支都是"等这一路"，只要没有 `default` 臂也没有超时分支，
这一行就是一个能永久阻塞的同步点 —— 静态闸门会拦它。

### 跨线程要写清事件顺序

并发测试要显式描述并控制顺序：操作开始 → 到达同步点 → 被释放或取消 → 终止。
用 channel、barrier 或可控测试替身，不要用 sleep 去"大概等一下"。

### 每个资源都要有主人和清理路径

`tokio::spawn`、`std::thread::spawn`、定时器、子进程、监听句柄，
成功和断言失败两条路径都要能收干净。断言前 drop 守卫比在测试末尾写清理更可靠。

### 断言可观察行为

不要为了让测试通过而放宽生产行为，也不要为了断言把私有状态提成 `pub`。
"取不到图标时静默回落"这类问题要用返回值或渲染结果来断言，不要去读内部字段。
